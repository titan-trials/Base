Retry the odds fetch, but only on failures that cannot have been billed

A failed odds pull costs a window that cannot be re-bought -- historical
odds are not on the free tier, so a game not priced before first pitch can
never be benchmarked by anyone. That argues for retrying. Player props are
billed PER EVENT against a 500-credit month, which argues for not.

The two mistakes are not symmetric, and that asymmetry is the whole design:

  give up too early   -> already_captured() reads odds_{date}.csv and
                         returns the games already held, so a re-run buys
                         only what is missing. Recoverable, free.

  retry too eagerly   -> the first request may have reached the server and
                         been billed. The retry is billed again. Nothing
                         gives that credit back.

So _get() -- the single HTTP choke point in data/odds_lines.py -- retries
only what provably never reached a server that could charge for it:
connection refused, connection reset, DNS failure, network unreachable, and
5xx the server itself sent. Three attempts, exponential backoff from 1.5s
with 25% jitter, under 10 seconds worst case so the retry cannot itself eat
a lock time.

Timeouts are NOT retried. Twenty seconds of silence is not proof the
request never arrived -- the API may have served a slow query and charged
for it while we stopped listening. A truncated body is not retried either:
a half-read answer is proof the server answered. 4xx is never retried; 401
is a bad key, 422 bad parameters, and 429 means the quota is gone and
asking again makes it worse. Ambiguity falls on the do-not-retry side by
construction.

No dependency added. odds_lines uses urllib, so the tenacity/requests
suggestion in improvement_plan.md was not needed -- only `socket` and
`random`.

test_odds_retry.py (53 checks) asserts on the NUMBER OF URLOPEN CALLS in
every case, because the call count is the credit count. Nothing touches the
network; urlopen and time.sleep are replaced. It covers the happy path, the
five never-retried failures, the eight retried ones, recovery on the second
and third try, and that the backoff is jittered and bounded. Part 6 asserts
already_captured is still the thing standing between a re-run and a second
bill -- if that ever stops skipping, this entire policy is wrong.
